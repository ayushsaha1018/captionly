# Auth, Projects & Snapshots — Design

**Date:** 2026-09-14
**Status:** design approved, spec written
**Branch:** new backend work happens on a separate branch (not yet created)
**Scope:** new workspace `apps/api` (Cloudflare Workers). No changes to `apps/studio`'s
existing local-only editing flow, `packages/engine`, or `apps/render`.

---

## 1. Goal

Add optional cloud accounts to captionly: sign in with Google, save projects (video +
subtitle document) to the cloud, and keep named/auto version history ("snapshots") of a
project's edit state, restorable across sessions and devices.

The app today is fully local/in-browser — no accounts, no server-side persistence, no
network dependency beyond `apps/render`'s optional server-export path. This is additive:
guest/local-only usage keeps working exactly as it does now. Login unlocks project
save/sync; it is never required to use the editor.

Explicitly **out of scope** for this round:
- Rendering/export changes. Both export paths (client WebCodecs, server via `apps/render`)
  are untouched — rendered output stays local-download-only. Storing rendered MP4s in the
  cloud is a future feature, not this one.
- Sharing/collaboration. Projects are solo-owned; no membership or roles model.
- Any auth provider other than Google.

---

## 2. Topology

```
apps/studio  (Cloudflare Pages, existing, separate domain from api)
     │  fetch() with Authorization: Bearer <session-token>
     ▼
apps/api     (NEW — Cloudflare Workers, Hono router)
     │                        │
     ▼                        ▼
Neon Postgres            Backblaze B2 (S3-compatible)
(Drizzle ORM,             presigned PUT/GET URLs —
 neon-http driver)        video bytes never transit the Worker
```

`apps/render` is unrelated to this design and is not touched.

**New workspace:** `apps/api`, following repo convention (Bun for local dev/tests). Router:
**Hono** — the standard lightweight router for Workers; it's what better-auth's own Workers
integration examples are built on, no heavier framework justified.

Studio and api will run on **separate, unrelated domains** (studio stays on Cloudflare
Pages; api on Workers free tier). This rules out cookie-based sessions (which require a
shared parent domain for cross-subdomain cookies) — see §3.

---

## 3. Auth

- `better-auth` core, mounted as a Hono route (`/auth/*`) — it's a plain fetch handler, runs
  natively on Workers, no special runtime adapter needed.
- `socialProviders: { google: { clientId, clientSecret, redirectURI } }` only. No
  email/password, no other providers — just omit them, nothing to explicitly disable.
- `drizzleAdapter(db, { provider: "pg" })` for the `users`/`sessions`/`accounts`/
  `verifications` tables, generated via better-auth's own schema CLI.
- **`bearer` plugin enabled.** Because studio and api are on unrelated domains, sessions
  can't ride on cookies. Client signs in via `/auth/sign-in/social`, gets a session token
  back, stores it (localStorage), and attaches `Authorization: Bearer <token>` on every
  subsequent API call. Sessions are DB-backed (looked up per request) — fine at this scale;
  no KV `secondaryStorage` needed unless session-check load becomes a real cost later.
- CORS on the Worker: allow the Pages origin + `Authorization` header. No
  `credentials: include` needed since nothing rides on cookies.
- Studio integration: a thin `useAuth` hook around better-auth's client. Logged out ⇒
  "save to cloud" / project UI is simply hidden; nothing calls `apps/api`. No change to
  `documentSlice`/`historySlice` or the existing local editing flow.

## 4. Data model

Postgres via Drizzle, `neon-http` driver (§6 explains the driver choice).

```
users, sessions, accounts, verifications   — owned/generated by better-auth

projects
  id            uuid pk
  user_id       fk -> users.id
  name          text
  video_key     text        -- B2 object key; null until a video is uploaded
  video_meta    jsonb        -- { width, height, durationSec, fps, mimeType }
  created_at, updated_at

snapshots
  id            uuid pk
  project_id    fk -> projects.id
  label         text         -- "Autosave" or a user-given name
  document      jsonb        -- the DocumentSnapshot verbatim (lines, style, animation, position)
  created_at
```

**Project = one video + one subtitle document.** Matches today's single `DocumentSnapshot`
model 1:1. Multi-video-per-project is a possible future extension, not designed for here.

**Projects are solo-owned** — `user_id` is a plain foreign key, no membership/roles table.
Every route's ownership check is `WHERE user_id = session.user.id`; a project that exists
but isn't the caller's returns 404, not 403 (don't leak existence).

**Snapshots are cloud save-points, separate from local undo/redo.** The existing
`historySlice` (in-session undo/redo over `DocumentSnapshot`) is untouched — it stays
unsaved, per-tab, exactly as today. A "snapshot" is an explicit, persisted version: created
on autosave (interval TBD at implementation time) and on manual "save version." It has no
relationship to `historySlice`'s past/future stacks.

**Retention:** capped per project (e.g. last 20 snapshots) rather than unlimited, enforced
in application logic — on insert, delete the oldest rows for that `project_id` beyond the
cap. This does not need a database transaction (see §6); an insert-then-delete-oldest
sequence is sufficient since a snapshot row is independent of every other row.

## 5. File storage (video)

- Backblaze B2, via its S3-compatible API (chosen over Cloudflare R2 to avoid R2's
  credit-card requirement).
- `aws4fetch` for request signing — a small Workers-native signing library, avoids the full
  AWS SDK's Node dependencies and bundle size.
- Upload: `POST /projects/:id/video-upload-url` returns a presigned PUT URL; the browser
  uploads directly to B2; the client then confirms via `PATCH /projects/:id` with the
  resulting key + `video_meta`. Download: `GET /projects/:id/video-url` returns a presigned
  GET URL on demand. Video bytes never pass through the Worker.

---

## 6. Database driver: Drizzle + Neon, no Hyperdrive

- **Drizzle over Prisma**, not a close call for Workers: Drizzle is edge-native (no
  Node-only deps, small bundle, first-class Neon HTTP driver). Prisma's Workers story needs
  the driver-adapters preview feature plus its own WASM query engine — more moving parts,
  historically flakier cold-start/bundle size on Workers.
- **`neon-http` driver** (`drizzle-orm/neon-http` + `@neondatabase/serverless`): each query
  is a single stateless HTTP request — no persistent connection to manage across a Worker's
  request-scoped lifetime. Every route in this design (§4's `projects`/`snapshots` tables)
  is single-row CRUD, so `neon-http`'s one limitation — no multi-statement interactive
  transactions — doesn't bite here.
- **Hyperdrive is not used.** Hyperdrive exists to pool/accelerate Worker→Postgres TCP
  connections for a Postgres that doesn't speak HTTP (RDS, a direct Supabase connection,
  etc.). Neon already solves that problem itself via its HTTP driver — Hyperdrive adds
  nothing on top of Neon.
- **If a future feature needs a real transaction** (multi-table atomic write), swap to
  `drizzle-orm/neon-serverless` (WebSocket-based, supports `db.transaction(...)`). The
  change is isolated to the single `apps/api/src/db.ts` connection-setup file — Drizzle's
  query builder API and every route handler are identical across both drivers, since all
  route code imports `db` from that one file rather than the driver package directly.
- **Free tier** (Neon): 100 CU-hours/project/month compute (scale-to-zero after 5 min idle,
  auto-resumes — plenty at solo-project scale), 0.5 GB storage/project, 5 GB egress/month,
  up to 10 branches/100 projects. Hitting a limit suspends compute or blocks over-cap
  writes; it does not delete data.
- **Local dev:** **Neon Local** (official Docker tool: local Postgres + a proxy container
  that speaks the same HTTP/WS protocol as Neon's cloud endpoint) via docker-compose. Keeps
  `apps/api`'s Drizzle setup byte-for-byte identical between local and deployed — only
  `DATABASE_URL` changes. (Plain local Postgres cannot be used by swapping the env var
  alone: `neon-http`/`neon-serverless` speak HTTP/WebSocket, not raw TCP, so they can't
  address vanilla Postgres directly — Neon Local is what bridges that gap.)

## 7. API surface (v1)

```
POST   /auth/*                          (better-auth; sign-in, sign-out, session, etc.)

GET    /projects                        list current user's projects
POST   /projects                        create
GET    /projects/:id
PATCH  /projects/:id                    rename, set video_key/video_meta
DELETE /projects/:id
POST   /projects/:id/video-upload-url   presigned B2 PUT url
GET    /projects/:id/video-url          presigned B2 GET url

GET    /projects/:id/snapshots          list (id, label, created_at only — not full document)
POST   /projects/:id/snapshots          create (enforces retention cap)
GET    /projects/:id/snapshots/:sid     fetch full document (for restore)
DELETE /projects/:id/snapshots/:sid
```

All routes except `/auth/*` require a valid bearer session, checked once via Hono
middleware (401 on failure) — not re-implemented per route.

---

## 8. Testing

Colocated `*.test.ts`, `bun test` — matching the rest of the repo. Route tests instantiate
the Hono app in-process and call it directly (no real network). Drizzle-layer/integration
tests run against Neon Local or a throwaway Neon branch, not mocked — consistent with this
repo's existing preference for real dependencies over mocks in tests that matter.

---

## 9. Open questions for implementation time

These don't block the plan but aren't nailed down yet:

- Autosave interval (time-based vs. debounced-on-change).
- Exact snapshot retention cap number (design above uses 20 as an illustrative default).
- Whether project deletion should cascade-delete its B2 video object immediately or on a
  delay/soft-delete.
